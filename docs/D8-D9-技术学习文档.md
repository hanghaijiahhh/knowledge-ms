## 二、MinIO 是什么

MinIO 是一个兼容 Amazon S3 API 的开源对象存储。可以理解为自己搭的"私有 AWS S3"。

**为什么不用服务器本地磁盘存文件？**
- 微服务多实例部署时，文件存 A 实例磁盘，B 实例读不到
- MinIO 是独立服务，所有实例共享访问
- 自带高可用、加密、版本管理

### 2.1 MinioClient Bean

```java
@Configuration
@ConfigurationProperties(prefix = "minio")
public class MinioConfig {
    private String endpoint;
    private String accessKey;
    private String secretKey;

    @Bean
    public MinioClient minioClient() {
        return MinioClient.builder()
                .endpoint(endpoint)
                .credentials(accessKey, secretKey)
                .build();
    }
}
```

`@ConfigurationProperties(prefix = "minio")` 把 `application.yml` 中的 `minio.*` 配置自动绑定到字段上：

```yaml
minio:
  endpoint: http://127.0.0.1:9000
  access-key: minioadmin
  secret-key: minioadmin
  bucket: knowledge-docs
```

## 三、小文件上传

### 3.1 流程

```
前端选择文件 → POST /file/upload (multipart/form-data)
    │
    ├─ 校验文件类型 (MIME白名单)
    ├─ 校验文件大小 (<10MB)
    ├─ 计算 MD5
    ├─ MinIO putObject → 存储到 bucket
    ├─ 写入 file_info 表
    └─ 返回 FileInfo (含 fileKey、size、md5)
```

### 3.2 实现

```java
@Override
@Transactional
public FileInfo upload(MultipartFile file, Long userId) {
    if (file.getSize() > SMALL_FILE_LIMIT) {
        throw new BizException("文件超过10MB，请使用分片上传");
    }
    validateFileType(file);

    String fileKey = generateFileKey(file.getOriginalFilename());
    String md5 = computeMd5(file);
    minioClient.putObject(PutObjectArgs.builder()
            .bucket(bucket)
            .object(fileKey)
            .stream(file.getInputStream(), file.getSize(), -1)
            .contentType(file.getContentType())
            .build());

    FileInfo info = new FileInfo();
    info.setFileKey(fileKey);
    info.setFileMd5(md5);
    // ...
    save(info);
    return info;
}
```

### 3.3 文件 Key 设计

```java
private String generateFileKey(String originalName) {
    String datePath = LocalDate.now().format(DateTimeFormatter.ofPattern("yyyy-MM"));
    return datePath + "/" + UUID.randomUUID().substring(0, 8) + "/" + originalName;
}
```

生成效果：`2026-06/3f7a2b1c/Spring Boot入门.pdf`

**为什么按日期分区？**
- MinIO 底层按前缀存储，按日期分区避免单个目录下文件过多
- 方便按时间范围做归档或清理
- UUID 短码防重名

### 3.4 文件类型校验

```java
private static final Set<String> ALLOWED_TYPES = Set.of(
    "application/pdf",
    "application/msword",
    "application/vnd.openxmlformats-officedocument...",
    "image/png", "image/jpeg", "image/gif",
    "text/plain", "text/markdown"
);
```

只允许传文档、图片、文本类文件。防止用户上传 exe、脚本等不安全文件类型。注意 `MultipartFile.getContentType()` 取自 HTTP 请求的 `Content-Type` 头，可以被伪造——生产环境应该结合文件魔数（Magic Number）做双重校验。

## 四、分片上传

### 4.1 为什么要分片

小文件（<10MB）直接一次上传就行。但大文件（500MB 的培训视频、100MB 的产品手册 PDF）如果一次上传：
- 网络断开就得从头再来
- 占用内存（整个文件 load 到内存再写 MinIO）
- 用户体验差（无进度反馈）

分片上传把大文件切成小块，逐块上传，全部上传完再合并。

### 4.2 三阶段流程

```
[1] POST /file/chunk/init
     │
     ├─ MD5秒传检测 → 命中则直接返回已有文件URL
     ├─ 生成 uploadId + fileKey
     ├─ Redis 记录元数据 (totalChunks, fileSize, ...)
     ├─ 创建 file_info 记录 (status=UPLOADING)
     └─ 返回 { uploadId, fileKey, skipUpload: false }

[2] POST /file/chunk/upload  (调用 N 次)
     │
     ├─ 从 Redis 读上传会话
     ├─ MinIO putObject → tmp/{uploadId}/{chunkIndex}
     └─ Redis 标记分片已上传 + 增加 uploadedCount

[3] POST /file/chunk/merge
     │
     ├─ 校验所有分片已到齐
     ├─ MinIO composeObject → 合并临时对象 → 最终文件
     ├─ 清理临时分片
     ├─ 更新 file_info 状态 → COMPLETED
     └─ 清理 Redis
```

### 4.3 初始化分片 + 秒传

```java
public ChunkInitResultDTO initChunkUpload(ChunkInitDTO dto, Long userId) {
    // 秒传：同样 MD5 + 同样大小的文件已存在 → 跳过上传
    if (dto.getFileMd5() != null) {
        FileInfo existing = getOne(new LambdaQueryWrapper<FileInfo>()
                .eq(FileInfo::getFileMd5, dto.getFileMd5())
                .eq(FileInfo::getFileSize, dto.getFileSize())
                .eq(FileInfo::getUploadStatus, "COMPLETED"));
        if (existing != null) {
            return new ChunkInitResultDTO(null, null, true, existing.getFileKey());
        }
    }

    String uploadId = UUID.randomUUID().toString().substring(0, 16);
    // Redis 记录上传元数据...
    return new ChunkInitResultDTO(uploadId, fileKey, false, null);
}
```

**秒传原理**：文件 MD5 指纹 + 文件大小构成唯一标识。同一份文件，不同用户上传，只需存一份。用户 A 上传过 `产品手册V3.pdf`（MD5=abc, size=50MB），用户 B 再上传同一份文件 → 直接返回已有的 fileKey。

### 4.4 分片合并

```java
// composeObject：将多个 MinIO 对象合并为一个，无需下载再上传
List<ComposeSource> sources = new ArrayList<>();
for (int i = 0; i < totalChunks; i++) {
    sources.add(ComposeSource.builder()
            .bucket(bucket)
            .object("tmp/" + uploadId + "/" + i)
            .build());
}
minioClient.composeObject(ComposeObjectArgs.builder()
        .bucket(bucket).object(fileKey).sources(sources).build());
```

**为什么用 composeObject 而不是下载后重新上传？**
- composeObject 是 MinIO/S3 服务端操作，数据不经过我们的服务器
- 合并 500MB 的文件，下载→重新上传需要 2× 网络传输 + 内存占用
- composeObject 在 MinIO 内部完成，速度快且不消耗应用服务器资源

**composeObject 的限制**：单次最多合并 1000 个源对象。如果分片数超过 1000，需要分批合并：

```
chunk_0 ... chunk_1499  (1500个分片)
    │
    ├─ batch_0: compose 0-999    → 中间文件 A
    ├─ batch_1: compose 1000-1499 → 中间文件 B
    │
    └─ compose A + B → 最终文件
```

代码中 `mergeSourcesInBatches` 方法递归处理了这种情况。

### 4.5 Redis 追踪上传进度

```
Redis Key                     Value (Hash)
─────────────                 ────────────
chunk:upload:{uploadId}       fileKey    → "2026-06/xxx/文件.pdf"
                              fileName   → "产品手册.pdf"
                              fileSize   → "52428800"
                              totalChunks → "10"
                              uploadedCount → "7"
                              TTL: 24h

chunk:parts:{uploadId}        "0" → "1"
                              "1" → "1"
                              ...
                              (标记哪些分片已上传)
```

**为什么用 Redis 而不是数据库记录分片状态？**
- 分片上传是临时状态，过期后无意义
- Redis TTL 自动清理过期会话（24 小时后自动删除）
- Hash 结构适合存 key-value 元数据，比数据库单表更轻量

## 五、文件下载

```java
public void download(Long fileId, HttpServletResponse response) {
    FileInfo info = getById(fileId);
    try (InputStream stream = minioClient.getObject(
            GetObjectArgs.builder().bucket(bucket).object(info.getFileKey()).build())) {

        response.setContentType(info.getFileType());
        response.setHeader("Content-Disposition",
                "attachment; filename=\"" + URLEncoder.encode(info.getOriginalName(), "UTF-8") + "\"");

        stream.transferTo(response.getOutputStream());
        response.flushBuffer();
    }
}
```

**为什么用流式输出而不是先读到内存？**
- `stream.transferTo(response.getOutputStream())` 是边读边写，不把整个文件 load 进内存
- 500MB 的文件如果用 `byte[] bytes = stream.readAllBytes()`，JVM 直接 OOM
- 流式输出内存占用恒定（只有 8KB 缓冲区）

## 六、关键面试知识点

1. **MinIO vs FastDFS vs OSS？**
   - MinIO：兼容 S3 API，部署简单（单文件二进制），适合私有化部署
   - FastDFS：老牌国产方案，需要 tracker + storage 多组件，部署复杂
   - 阿里云 OSS / AWS S3：云厂商托管，按量付费，免运维但花钱

2. **分片上传和断点续传的关系？**
   - 分片上传是实现断点续传的基础
   - 断点续传 = 分片上传 + 前端记录已上传分片列表
   - 网络断开 → 重连 → 前端只上传未完成的分片 → 合并
   - 当前实现支持断点续传：Redis 记录了已上传的分片，重复上传同一个 uploadId 会跳过已有分片

3. **秒传是怎么实现的？**
   - 前端在 init 阶段传文件的 MD5 + 总大小
   - 后端查 `file_info WHERE file_md5 = ? AND file_size = ? AND upload_status = 'COMPLETED'`
   - 命中 → 返回已有 fileKey，前端直接关联到文档，跳过所有上传步骤
   - MD5 碰撞概率极低（2^128 分之一），结合文件大小做双重校验足够可靠

4. **为什么 composeObject 比"下载后重新上传"好？**
   - 服务端操作 vs 客户端操作：MinIO 内部完成合并，数据不经过应用服务器
   - 速度：MinIO 内部合并走存储层 I/O，比应用服务器下载→上传少一次网络往返
   - 带宽：不消耗应用服务器的入口/出口带宽

5. **文件上传的安全考量？**
   - 类型白名单：只允许特定 MIME 类型
   - 大小限制：小文件 <10MB，分片场景前端按 chunk 大小切分
   - 生产环境还需：文件魔数校验（防 MIME 伪造）、病毒扫描、用户上传频率限制
