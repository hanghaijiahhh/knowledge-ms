## 二、为什么需要审计日志

企业知识库系统有合规需求：谁在什么时间对什么文档做了什么操作，必须有据可查。比如：

- 合规审计："上月谁修改了薪酬制度文档？"
- 安全排查："怀疑有人恶意删除文档，查一下删除记录"
- 溯源："这份文档的内容是谁、什么时候改的？"

审计日志和版本管理的区别：
- 版本管理记录的是"文档内容变到什么版本"（数据视角）
- 审计日志记录的是"谁做了什么操作"（安全视角）
- 两者互补，一个关注 What，一个关注 Who+When

## 三、数据库设计

### 3.1 表结构

```sql
CREATE TABLE audit_log (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    doc_id BIGINT COMMENT '关联文档ID',
    doc_title VARCHAR(255) COMMENT '文档标题（冗余，历史标题）',
    action VARCHAR(20) COMMENT '操作类型：CREATE/UPDATE/DELETE/VIEW',
    operator_id BIGINT COMMENT '操作人ID',
    operator_name VARCHAR(100) COMMENT '操作人用户名',
    detail TEXT COMMENT '操作详情（JSON 格式，如变更字段、旧值/新值）',
    ip_address VARCHAR(45) COMMENT '客户端IP',
    create_time DATETIME COMMENT '操作时间',
    INDEX idx_doc_id (doc_id),
    INDEX idx_operator_id (operator_id),
    INDEX idx_create_time (create_time)
);
```

### 3.2 设计要点

**为什么冗余 doc_title？** 文档可能被删除，如果只存 doc_id，日志里显示"文档#123 被删除"，看不懂。冗余标题后日志显示"《薪酬制度 V3》被删除"——信息完整。

**detail 用 TEXT + JSON 格式**：不同操作类型的详情结构不同：
- CREATE：`{"title": "新文档", "status": "PUBLISHED"}`
- UPDATE：`{"changedFields": ["title", "content"], "oldVersion": 3}`
- DELETE：`{"version": 5, "lastUpdateTime": "2026-06-01T10:00:00"}`

用 JSON 灵活存储，不限制 schema。

**三个索引**：按文档查、按操作人查、按时间范围查——覆盖最常见的三种审计查询。

## 四、MQ 消费者

### 4.1 事件订阅

```java
@Component
public class AuditLogConsumer {

    @RabbitListener(queues = "knowledge.audit.queue")
    public void handleDocEvent(Map<String, Object> payload) {
        AuditLog log = new AuditLog();
        log.setDocId(((Number) payload.get("docId")).longValue());
        log.setDocTitle((String) payload.get("title"));
        log.setAction(deduceAction(payload));
        log.setOperatorId(((Number) payload.get("userId")).longValue());
        log.setOperatorName((String) payload.get("username"));
        log.setDetail(JSON.toJSONString(payload));
        log.setCreateTime(LocalDateTime.now());

        auditLogService.save(log);
    }
}
```

### 4.2 操作类型推断

从 routing key 推断操作类型：

```java
// RabbitMQ 消息头中包含 routing key
private String deduceAction(Map<String, Object> payload) {
    // 从 payload 中获取事件类型标记
    String action = (String) payload.get("action");
    if (action == null) {
        // 兼容旧消息：从 routing key 推断
        return "UNKNOWN";
    }
    return switch (action) {
        case "doc.create" -> "CREATE";
        case "doc.update" -> "UPDATE";
        case "doc.delete" -> "DELETE";
        default -> "UNKNOWN";
    };
}
```

## 五、查询接口

```java
@RestController
@RequestMapping("/audit")
public class AuditLogController {

    @GetMapping("/list")
    public ResponseResult<IPage<AuditLog>> list(
            @RequestParam(defaultValue = "1") Integer pageNum,
            @RequestParam(defaultValue = "20") Integer pageSize,
            @RequestParam(required = false) Long docId,
            @RequestParam(required = false) Long operatorId) {

        LambdaQueryWrapper<AuditLog> wrapper = new LambdaQueryWrapper<>();
        if (docId != null) wrapper.eq(AuditLog::getDocId, docId);
        if (operatorId != null) wrapper.eq(AuditLog::getOperatorId, operatorId);
        wrapper.orderByDesc(AuditLog::getCreateTime);

        return ResponseResult.success(auditLogService.page(
            new Page<>(pageNum, pageSize), wrapper));
    }
}
```

## 六、事件发布端的改造

在 `knowledge-doc` 的 `DocInfoServiceImpl.publishEvent()` 中，payload 已包含相关信息：

```java
private Map<String, Object> buildEventPayload(DocInfo doc, Long userId, String username) {
    Map<String, Object> payload = new HashMap<>();
    payload.put("docId", doc.getId());
    payload.put("title", doc.getTitle());
    payload.put("content", doc.getContent());   // audit 不需要此字段但 search 需要
    payload.put("categoryId", doc.getCategoryId());
    payload.put("status", doc.getStatus());
    payload.put("userId", userId);
    payload.put("username", username);
    payload.put("timestamp", System.currentTimeMillis());
    return payload;
}
```

审计消费者只关注 `docId`、`title`、`userId`、`username`、`timestamp`，其他字段记录在 detail 中。

## 七、关键面试知识点

1. **审计日志为什么用 MQ 而不是同步写？**
   - 审计是辅助功能，不应阻塞主业务（文档保存）
   - MQ 异步写入，即使审计服务挂了，文档功能正常
   - MQ 保证投递可靠性（持久化 + 消息确认）

2. **审计日志和操作日志的区别？**
   - 审计日志：面向合规，"谁在什么时间做了什么"，不可篡改
   - 操作日志：面向开发排查，"为什么搜索返回 500"，可随时清理
   - 审计日志有法律效力，需要长期保存

3. **为什么存 doc_title 而非只存 doc_id？**
   - 文档删除后 doc_id 无意义
   - 冗余标题让日志可读性大大提升
   - 少量冗余存储换取长期可读性——合理权衡

4. **审计日志的存储压力？**
   - 每个文档操作一条记录，每条约 0.5KB
   - 日均 1000 次操作 → 0.5MB/天 → 180MB/年
   - MySQL 完全可以承受，无需特殊处理
   - 海量场景可考虑按月分表或迁移到 ES
