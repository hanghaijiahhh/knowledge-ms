## 二、两级权限模型

### 2.1 RBAC vs ACL 的职责边界

```
RBAC (sys_role_menu)        ACL (doc_acl)
───────────────              ──────────────
管"能不能进这个页面"        管"能不能看这篇文档"
粒度: 菜单级                 粒度: 单文档级
用户注册时分配角色           文档创建后单独授权
```

**为什么需要两级？**

RBAC 只能控制到菜单——用户有 `doc:list` 权限就能进文档列表页。但进了列表页，不代表他能看所有文档。比如 HR 部门的薪酬文档，只应该让 HR 组的成员看。

ACL 做的是"这篇文档谁能读、谁能改"。RBAC 和 ACL 各管一个维度，互不冲突。

### 2.2 数据表设计

```sql
doc_acl:
id | doc_id | user_id | perm_read | perm_write | perm_download | granted_by
1  | 100    | 5       | 1         | 0          | 0             | 1
```

每位（bit）代表一种权限，0=无，1=有。不用的权限直接设 0，而不是存一个"角色"。这样不同用户可以有不同的权限组合——用户 A 只能读，用户 B 能读写但不能下载。

### 2.3 权限判定逻辑

```java
public boolean hasPermission(Long docId, Long userId, String permission) {
    DocInfo doc = docInfoMapper.selectById(docId);
    // 创建者拥有全部权限
    if (doc.getCreatorId().equals(userId)) return true;

    // 查 ACL 表
    DocAcl acl = getOne(new LambdaQueryWrapper<DocAcl>()
            .eq(DocAcl::getDocId, docId)
            .eq(DocAcl::getUserId, userId));
    if (acl == null) return false;

    return switch (permission) {
        case "read"     -> acl.getPermRead() == 1;
        case "write"    -> acl.getPermWrite() == 1;
        case "download" -> acl.getPermDownload() == 1;
        default -> false;
    };
}
```

**关键设计决策**：创建者隐式拥有全部权限，不需要额外在 ACL 表里给自己加一条记录。这避免了创建文档时还得插一条 ACL 的冗余操作。

## 三、AOP 权限切面

### 3.1 为什么用 AOP

不用 AOP 的做法：

```java
// 每个接口开头都要写这段
if (!docAclService.hasPermission(docId, userId, "write")) {
    throw new BizException("无权操作");
}
// ... 业务代码
```

7 个接口 × 3 行 = 21 行重复代码。而且哪天想加个"权限被拒日志"，得改 7 个地方。

用 AOP 的做法：

```java
@PutMapping("/{id}")
@CheckDocPermission("write")   // 一行注解搞定
public ResponseResult<DocInfo> update(...) { ... }
```

权限逻辑集中在一个切面里，Controller 只关心业务。

### 3.2 注解定义

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface CheckDocPermission {
    String value() default "read";       // read / write / download
    String paramName() default "id";     // 方法参数中哪个是 docId
}
```

两个参数：
- `value`：需要哪种权限
- `paramName`：方法参数名，用于反射提取 docId 的值（默认叫 "id"）

### 3.3 切面实现

```java
@Aspect
@Component
public class DocPermissionAspect {

    @Before("@annotation(checkPermission)")
    public void checkPermission(JoinPoint jp, CheckDocPermission checkPermission) {
        // 1. 从方法参数中提取 docId
        Long docId = extractDocId(jp, checkPermission.paramName());
        if (docId == null) return;

        // 2. 从 Gateway Header 取当前用户
        Long userId = userContextUtil.getCurrentUserId();

        // 3. 校验权限
        docAclService.checkPermission(docId, userId, checkPermission.value());
    }
}
```

`extractDocId` 通过反射拿到方法参数名和参数值的对应关系：

```java
private Long extractDocId(JoinPoint jp, String paramName) {
    MethodSignature signature = (MethodSignature) jp.getSignature();
    Parameter[] params = signature.getMethod().getParameters();
    Object[] args = jp.getArgs();

    for (int i = 0; i < params.length; i++) {
        if (params[i].getName().equals(paramName) && args[i] instanceof Long) {
            return (Long) args[i];
        }
    }
    return null;
}
```

这里用了一个细节：Spring 默认不会保留方法参数名（`javac -parameters` 开启后才会）。但 Spring Boot 的编译插件默认启用了 `-parameters`，所以 `params[i].getName()` 能正常工作。

### 3.4 集成效果

```java
// 查单个文档 → 需要读权限
@GetMapping("/{id}")
@CheckDocPermission("read")
public ResponseResult<DocInfo> getById(@PathVariable Long id)

// 更新文档 → 需要写权限
@PutMapping("/{id}")
@CheckDocPermission("write")
public ResponseResult<DocInfo> update(@PathVariable Long id, ...)

// 删除文档 → 需要写权限
@DeleteMapping("/{id}")
@CheckDocPermission("write")
public ResponseResult<?> delete(@PathVariable Long id)

// ACL 授权接口本身也需要写权限
@PostMapping("/{id}/acl")
@CheckDocPermission("write")
public ResponseResult<?> grant(@PathVariable Long id, ...)
```

**创建文档（POST /doc）不需要加权限注解**——文档还不存在，没有 ACL 记录可查。谁创建谁就是 owner，天然有全部权限。

**分页查询（GET /doc/page）也没有加**——因为列表查询涉及多条记录，逐条 ACL 校验性能太差。实际做法是在查询层做过滤（只查 creator_id = 自己 OR doc_acl 中有授权的），当前阶段先返回全量，留到前端配合权限做展示过滤。

## 四、关键面试知识点

1. **RBAC 和 ACL 的区别？**
   - RBAC：基于角色的访问控制，"你是管理员所以能进用户管理页"
   - ACL：基于访问控制列表，"这篇文档对张三开放了读权限"
   - 实际系统通常两级都用：RBAC 管大粒度（菜单/功能），ACL 管小粒度（数据行/文档）

2. **为什么不用 Spring Security 的 `@PreAuthorize` 而是自己写注解？**
   - `@PreAuthorize` 的 SpEL 表达式可以做方法级鉴权，但它校验的是 Authentication 里的 GrantedAuthority
   - ACL 的权限粒度到单篇文档，需要动态查数据库——`@PreAuthorize` 做不到"查 doc_acl 表判断用户对 docId=123 是否有 read 权限"
   - 自写 AOP 可以自由地从方法参数取 docId、调 Service 查 ACL 表，灵活性更高

3. **AOP 切面在什么时候执行？**
   - `@Before` 注解表示在目标方法执行**之前**拦截
   - 如果权限校验失败抛出 BizException → 被 GlobalExceptionHandler 捕获 → 返回错误 JSON
   - 目标方法不会被执行，业务代码完全不知情

4. **创建者为什么自动有全部权限？**
   - 避免创建文档后还得额外插一条 ACL 记录的冗余操作
   - 如果创建者想把文档授权给别人，走 POST /doc/{id}/acl 接口单独授权
   - 这个规则写死在 `hasPermission` 方法里，不是数据库约束，灵活可改
