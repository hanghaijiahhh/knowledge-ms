# D1 技术学习文档：项目骨架与技术选型

## 一、为什么选择这个技术栈

### 1.1 SpringCloud Alibaba vs SpringCloud Netflix

作为应届生简历项目，选 SpringCloud Alibaba 有几点考虑：

- Netflix 体系（Eureka + Ribbon + Hystrix）大部分已进入维护模式
- Alibaba 体系（Nacos + Sentinel + RocketMQ）在国内企业中使用更广
- Nacos 同时做注册中心和配置中心（Eureka + Config 二合一），减少运维组件

### 1.2 版本选择

```
Spring Boot 3.5.15    → 最新的 3.x 稳定版（JDK 17 最低要求）
Spring Cloud 2025.0.0 → 对应 Boot 3.5.x
SpringCloud Alibaba 2025.0.0.0 → 对应 Cloud 2025.0.0
JDK 17                 → LTS 版本，生产主流
```

**版本对齐非常重要**。Spring Boot → Spring Cloud → SpringCloud Alibaba 三者有严格的版本映射关系，错一个就启动报错。查官方 Wiki：https://github.com/alibaba/spring-cloud-alibaba/wiki/版本说明

### 1.3 核心组件选型

| 组件 | 选型 | 备选方案 | 选型理由 |
|------|------|---------|---------|
| 注册中心/配置中心 | Nacos 2.x | Eureka + Config | 二合一，阿里内部验证 |
| 网关 | Spring Cloud Gateway | Zuul 1.x | 基于 WebFlux，性能更好 |
| RPC 调用 | OpenFeign | Dubbo | Spring 生态集成度更高 |
| 消息队列 | RabbitMQ | RocketMQ / Kafka | 部署简单，学习成本最低 |
| ORM | MyBatis-Plus 3.5.9 | JPA | SQL 控制力强，Lambda 条件构造器 |
| 搜索引擎 | Elasticsearch 8.x | Solr | 生态更大，Dense Vector 支持好 |
| 对象存储 | MinIO | OSS / FastDFS | 兼容 S3 API，私有化部署 |
| 数据库 | MySQL 8.0 | PostgreSQL | 国内使用最广 |

## 二、Maven 多模块结构

### 2.1 为什么拆成多模块

单体项目一个 module 就够了，但微服务项目必须多模块：

- **代码复用**：`ResponseResult`、`BizException` 等公共类放 common 模块，所有服务共享
- **独立部署**：auth、doc、file 各自打包成独立 jar，可以单独扩缩容
- **依赖隔离**：Gateway 不需要连接数据库，就不应该引入 MyBatis-Plus

### 2.2 模块依赖树

```
knowledge-ms (pom)                     ← 父工程，定义版本号 + dependencyManagement
├── knowledge-common                   ← 公共模块：DTO、异常、工具类、自动配置
│   └── 依赖：spring-web, lombok, fastjson, knife4j, jakarta.servlet-api(provided)
├── knowledge-gateway                  ← 网关：8080
│   └── 依赖：common, spring-cloud-starter-gateway, jjwt, knife4j-gateway
├── knowledge-auth                     ← 认证服务：8081
│   └── 依赖：common, spring-boot-starter-web, spring-security, mybatis-plus, mysql
├── knowledge-doc                      ← 文档服务：8082
│   └── 依赖：common, web, mybatis-plus, mysql, rabbitmq, openfeign, loadbalancer
├── knowledge-file                     ← 文件服务：8083
│   └── 依赖：common, web, mybatis-plus, mysql, minio, pdfbox, openfeign

```

### 2.3 父工程 POM 核心内容

```xml
<!-- packaging 必须是 pom -->
<packaging>pom</packaging>

<parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>3.5.15</version>
</parent>

<properties>
    <java.version>17</java.version>
    <spring-cloud-alibaba.version>2025.0.0.0</spring-cloud-alibaba.version>
    <spring-cloud.version>2025.0.0</spring-cloud.version>
    <mybatis-plus.version>3.5.9</mybatis-plus.version>
    <mysql.version>8.0.33</mysql.version>
    <hutool.version>5.8.29</hutool.version>
    <lombok.version>1.18.30</lombok.version>
</properties>

<!-- dependencyManagement：统一管理版本，子模块引用时不用写版本号 -->
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.springframework.cloud</groupId>
            <artifactId>spring-cloud-dependencies</artifactId>
            <version>${spring-cloud.version}</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
        <dependency>
            <groupId>com.alibaba.cloud</groupId>
            <artifactId>spring-cloud-alibaba-dependencies</artifactId>
            <version>${spring-cloud-alibaba.version}</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
        <!-- MyBatis-Plus, MySQL 驱动, Lombok, Hutool 等统一在此声明 -->
    </dependencies>
</dependencyManagement>
```

**关键理解**：`dependencyManagement` 只声明版本不实际引入。子模块需要在自己的 `<dependencies>` 中显式引用，但不写版本号。

### 2.4 为什么 Gateway 的 common 依赖要特殊处理

Gateway 基于 WebFlux（Netty），不能引入 Tomcat。但 common 模块原本依赖了 `spring-boot-starter-web`（包含 Tomcat）。

**解决方案**：common 模块不依赖 starter-web，改为细粒度依赖：

```xml
<!-- common 模块的 pom.xml -->
<dependencies>
    <!-- 只引入 web 的基础注解和工具（如 @RestController, HttpServletRequest） -->
    <dependency>
        <groupId>org.springframework</groupId>
        <artifactId>spring-web</artifactId>
    </dependency>
    <!-- servlet-api 声明为 provided：编译期可用，但不传递到下游模块 -->
    <dependency>
        <groupId>jakarta.servlet</groupId>
        <artifactId>jakarta.servlet-api</artifactId>
        <scope>provided</scope>
    </dependency>
    <!-- ... -->
</dependencies>
```

`scope=provided` 的含义：编译时需要，打包时由容器提供。Gateway 不引入 servlet-api，所以不会产生 WebFlux vs MVC 冲突。

## 三、Nacos 注册中心 + 配置中心

### 3.1 启动 Nacos

```bash
# Windows (单机模式)
startup.cmd -m standalone

# 默认地址：http://localhost:8848/nacos
# 默认账号：nacos / nacos
```

### 3.2 每个微服务的 Nacos 配置

```yaml
# application.yml（每个服务都有这段）
spring:
  application:
    name: knowledge-auth       # 服务名 → 注册到 Nacos 的名字
  cloud:
    nacos:
      discovery:
        server-addr: 127.0.0.1:8848   # Nacos 地址
      config:
        server-addr: 127.0.0.1:8848
        file-extension: yaml
```

**服务启动后，Nacos 控制台 → 服务管理 → 服务列表**中应该能看到所有注册的服务。

### 3.3 Nacos 的两个功能

| | 注册中心 (Discovery) | 配置中心 (Config) |
|---|---|---|
| 做什么 | 记录"哪个服务的哪个实例在哪个 IP:Port 运行" | 集中管理配置文件，修改后热刷新 |
| 类似 | DNS（域名 → IP） | Apollo / Spring Cloud Config |
| 本项目使用 | ✅ 必须（服务发现 + 负载均衡） | ❌ 未使用（配置直接写 application.yml） |

**为什么本项目没用 Nacos 配置中心？** 个人项目配置量少，直接写 YAML 更简单。企业项目配置多且有灰度发布需求时，配置中心是必需的。

## 四、common 模块设计

### 4.1 统一响应体

```java
// 所有 Controller 都用这个返回格式，前端统一解析
@Data
public class ResponseResult<T> {
    private int code;
    private String message;
    private T data;

    public static <T> ResponseResult<T> success(T data) {
        ResponseResult<T> r = new ResponseResult<>();
        r.code = 200;
        r.message = "success";
        r.data = data;
        return r;
    }

    public static <T> ResponseResult<T> fail(int code, String message) {
        ResponseResult<T> r = new ResponseResult<>();
        r.code = code;
        r.message = message;
        return r;
    }
}
```

前端收到的 JSON 格式始终是 `{ "code": 200, "message": "success", "data": {...} }`。

### 4.2 全局异常处理

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(BizException.class)
    public ResponseResult<?> handleBiz(BizException e) {
        return ResponseResult.fail(400, e.getMessage());
    }

    @ExceptionHandler(Exception.class)
    public ResponseResult<?> handleException(Exception e) {
        log.error("系统异常", e);
        return ResponseResult.fail(500, "服务器内部错误");
    }
}
```

**为什么需要这个？** 否则 Controller 抛异常时前端直接收到 Tomcat 的 HTML 错误页，JSON 解析失败。

### 4.3 自动配置注册

`UserContextUtil`、`GlobalExceptionHandler` 等放在 common 模块，但 Spring 默认只扫描启动类所在包。需要注册为自动配置：

```java
// common 模块中
@AutoConfiguration
@Import({UserContextUtil.class, GlobalExceptionHandler.class})
public class CommonAutoConfiguration {
}
```

同时创建文件 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`：
```
com.myy.common.config.CommonAutoConfiguration
```

这是 Spring Boot 3.x 新的自动配置注册方式（替代了旧的 `spring.factories`）。

### 4.4 RabbitMQ 常量

```java
public class RabbitMQConstant {
    public static final String DOC_EXCHANGE = "knowledge.doc.exchange";
    // routing keys
    public static final String ROUTING_DOC_CREATE = "doc.create";
    public static final String ROUTING_DOC_UPDATE = "doc.update";
    public static final String ROUTING_DOC_DELETE = "doc.delete";
    public static final String ROUTING_DOC_EMBED  = "doc.embed";
}
```

常量化 exchange/queue/routing-key 名称，避免多个服务写字符串拼错。

### 4.5 配置外部化（.env + EnvironmentPostProcessor）

数据库密码、API Key、JWT 密钥等敏感配置不硬编码在各模块 yml，而是抽离到父项目根目录的 `.env` 文件（已 gitignore），通过自定义 `EnvironmentPostProcessor` 在启动时加载。

**为什么用 EnvironmentPostProcessor？**
- 它是最早的 Spring Boot 扩展点之一，在 application.yml 解析前执行，保证 `${DB_PASS}` 占位符能解析到 .env 里的值
- 放在 common 模块，所有依赖 common 的服务自动生效，无需每个模块单独配置

```java
public class DotenvEnvironmentPostProcessor implements EnvironmentPostProcessor {
    public void postProcessEnvironment(ConfigurableEnvironment env, SpringApplication app) {
        // 从工作目录向上逐级查找 .env（兼容 IDEA 以模块目录为工作目录）
        // 解析 KEY=VALUE 注入 MapPropertySource
        // addLast 放在最后：真实环境变量优先于 .env 文件
    }
}
```

**注册方式**：EnvironmentPostProcessor 仍用 `META-INF/spring.factories` 注册（注意：不是 `AutoConfiguration.imports`，那是给 `@AutoConfiguration` 用的）。

**优先级设计**：`addLast` 把 .env 放在 property source 末尾，意味着真实环境变量 > .env 文件。生产环境可注入真实环境变量覆盖 .env 的本地开发值。

**为什么不用 Nacos 配置中心？** 个人项目配置量少，.env + EnvironmentPostProcessor 已够用且更轻量；企业项目配置多、需灰度发布时再引入 Nacos Config。

## 六、启动顺序

```
1. MySQL（必须最先启动）
2. Nacos（服务注册与发现的基础）
3. Redis（缓存）
4. RabbitMQ（消息队列）
5. Elasticsearch（搜索引擎）
6. MinIO（对象存储）

7. knowledge-auth      ← 先启动，其他服务可能需要认证
8. knowledge-doc       ← 文档服务
9. knowledge-file      ← 文件服务
10. knowledge-search   ← 搜索服务
11. knowledge-embedding ← 嵌入服务
12. knowledge-audit    ← 审计服务
13. knowledge-agent    ← AI Agent
14. knowledge-gateway  ← 网关最后启动，前面服务都就绪再对外暴露

15. knowledge-ui       ← 前端（npm run dev）
```

**为什么 Gateway 最后启动？** Gateway 启动时从 Nacos 拉取路由表。如果下游服务还没注册，路由表为空，请求会 404。

## 七、关键面试知识点

1. **为什么拆成多模块而不是一个大项目？**
   - 代码复用（common 模块）
   - 独立部署和扩缩容（doc 服务压力大可以部署 3 台，auth 只要 1 台）
   - 依赖隔离（Gateway 不依赖 MySQL 驱动）
   - 团队协作（不同人负责不同模块）

2. **Nacos 和 Eureka 的区别？**
   - Nacos 同时做注册中心 + 配置中心，Eureka 只做注册中心
   - Nacos 支持 AP/CP 模式切换，Eureka 只有 AP
   - Nacos 使用 Raft 协议保证一致性，Eureka 是 peer-to-peer 复制

3. **为什么 Maven scope=provided？**
   - 编译时需要，但运行时由容器提供
   - `provided` 不会传递到依赖该模块的下游模块
   - Gateway 因此不会继承 servlet-api，避免了 WebFlux 冲突

4. **Spring Boot 3.x 的自动配置机制变化？**
   - 旧：`META-INF/spring.factories` 注册 `EnableAutoConfiguration`
   - 新：`META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`
   - `@AutoConfiguration` 替代 `@Configuration`（语义更明确）
