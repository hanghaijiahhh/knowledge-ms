## 二、文档版本管理

### 2.1 核心设计

```
上传文件 → 创建文档(version=1) → 在doc_version表保存v1快照
                │
          用户上传新文件
                │
                ▼
          更新文档(version=2) → v1旧文件存入doc_version
                │
          用户回滚到v1
                │
                ▼
          从doc_version取v1的文件URL覆盖当前文档
          → version变成3(回滚操作本身也是一个新版本)
```

### 2.2 实现代码

```java
@Override
@Transactional
public DocInfo updateDoc(Long docId, DocUpdateDTO dto, Long userId) {
    DocInfo doc = getById(docId);

    if (StringUtils.hasText(dto.getFileUrl())) {
        int newVersion = doc.getVersion() + 1;
        // 保存旧版本快照
        saveVersion(docId, newVersion, dto.getFileUrl(), dto.getFileSize(),
                dto.getChangeDesc(), userId);
        doc.setVersion(newVersion);
        doc.setFileName(dto.getFileName());
        doc.setFileUrl(dto.getFileUrl());
    }

    if (StringUtils.hasText(dto.getTitle())) doc.setTitle(dto.getTitle());
    updateById(doc);
    publishEvent("doc.update", ...);
    return doc;
}
```

**关键点**：
- 只有上传新文件才触发版本号递增。只改标题/分类不触发。
- `@Transactional` 保证 doc_info 更新和 doc_version 插入是原子操作——要么都成功，要么都失败。
- 回滚操作本身也是一个新版本（不回退版本号，而是生成 version n+1）。

### 2.3 版本回滚

```java
@Override
@Transactional
public DocInfo revertVersion(Long docId, Integer targetVersion, Long userId) {
    DocVersion targetVer = versionMapper.selectOne(
        new LambdaQueryWrapper<DocVersion>()
            .eq(DocVersion::getDocId, docId)
            .eq(DocVersion::getVersion, targetVersion));

    // 用目标版本的fileUrl覆盖当前文档
    doc.setFileUrl(targetVer.getFileUrl());
    doc.setVersion(doc.getVersion() + 1);
    updateById(doc);

    // 记录回滚操作
    saveVersion(docId, doc.getVersion(), targetVer.getFileUrl(), ...,
        "回滚到版本 " + targetVersion, userId);
    return doc;
}
```

**为什么不直接修改 version 字段？**

版本表是追加写的（append-only），每个操作留痕。直接改 version 字段意味着失去了"回滚到 v1"这个操作本身的记录。

## 三、分类树

### 3.1 设计思路

```sql
doc_category:
id | parent_id | name
1  | 0         | 技术文档     ← 根分类
2  | 1         | Java        ← 子分类
3  | 1         | Python
4  | 2         | Spring      ← 孙分类
```

**parent_id = 0 表示根节点**。树结构用 parent_id 自引用，而不是邻接表或嵌套集——最简单、最直观。

### 3.2 递归组装树

```java
public List<DocCategory> getCategoryTree() {
    List<DocCategory> all = list();
    Map<Long, List<DocCategory>> childrenMap = all.stream()
        .filter(c -> c.getParentId() != 0)
        .collect(Collectors.groupingBy(DocCategory::getParentId));

    List<DocCategory> roots = new ArrayList<>();
    for (DocCategory c : all) {
        if (c.getParentId() == 0) {
            roots.add(c);
            buildChildren(c, childrenMap);
        }
    }
    return roots;
}
```

**时间复杂度 O(n)**：一次查出所有分类，内存里分组组装。不用递归查数据库（N+1 问题）。

### 3.3 递归删除

```java
@Override
@Transactional
public void deleteCategory(Long id) {
    // 先递归删子分类
    List<DocCategory> children = list(
        new LambdaQueryWrapper<DocCategory>().eq(DocCategory::getParentId, id));
    for (DocCategory child : children) {
        deleteCategory(child.getId());  // 递归
    }
    removeById(id);
}
```

删除父分类时，自动级联删除所有子分类。

## 四、RabbitMQ 事件驱动

### 4.1 为什么用 MQ

```
文档变更 → 同步调用搜索服务重新索引？  ← 坏做法
文档变更 → 发MQ消息 → 搜索服务异步消费  ← 好做法
```

**同步的问题**：
- 用户上传文档后要等 ES 索引完成才能收到响应——慢
- 搜索服务挂了，文档创建也失败——耦合

**MQ 的好处**：
- 发完消息就返回，ES 索引异步做——快
- 搜索服务挂了不影响文档创建——解耦
- 审计服务也可以订阅同一个消息做操作记录——一对多广播

### 4.2 配置

```java
@Configuration
public class RabbitMQConfig {

    @Bean
    public TopicExchange docExchange() {
        return new TopicExchange("knowledge.doc.exchange");
    }

    @Bean
    public Queue docCreateQueue() {
        return new Queue("knowledge.doc.create.queue", true);  // durable=true
    }

    @Bean
    public Binding bindingCreate() {
        return BindingBuilder
            .bind(docCreateQueue())
            .to(docExchange())
            .with("doc.create");  // routing key
    }
}
```

**TopicExchange**：根据 routing key 匹配队列。`doc.create` → 创建队列，`doc.update` → 更新队列，`doc.delete` → 删除队列。不同消费者可以订阅不同的 key。

### 4.3 发布事件

```java
private void publishEvent(String routingKey, Map<String, Object> payload) {
    rabbitTemplate.convertAndSend(
        RabbitMQConstant.DOC_EXCHANGE,  // exchange
        routingKey,                       // routing key
        payload                           // 消息体
    );
}
```

消息体是一个 `Map`，包含 docId、title、content、userId、timestamp 等字段。消费者收到后用 JSON 反序列化。

### 4.4 事件流向

```
doc.create ─→ knowledge.doc.create.queue ─→ SearchService (索引)
           ─→ knowledge.audit.queue       ─→ AuditService  (记录)

doc.update ─→ knowledge.doc.update.queue ─→ SearchService (更新索引)
           ─→ knowledge.audit.queue       ─→ AuditService  (记录)

doc.delete ─→ knowledge.doc.delete.queue ─→ SearchService (删除索引)
           ─→ knowledge.audit.queue       ─→ AuditService  (记录)
```

**注意**：队列在当前阶段只是声明了，消费者在后续 D11-D13 实现。

## 五、从 Gateway Header 取用户信息

### 5.1 数据流回顾

```
[Gateway AuthFilter]
    │
    JWT 校验通过
    │
    Claims → JSON → Base64 → 写入 X-User-Info Header
    │
    ▼
[Doc Service]
    │
    UserContextUtil 从 X-User-Info 解码
    │
    拿到 userId、username
```

### 5.2 实现

```java
@Component
public class UserContextUtil {

    public Long getCurrentUserId() {
        return Long.valueOf(getClaim("userId"));
    }

    private String getClaim(String key) {
        // 从当前请求的 Header 中取 X-User-Info
        HttpServletRequest request = ((ServletRequestAttributes)
            RequestContextHolder.getRequestAttributes()).getRequest();
        String encoded = request.getHeader("X-User-Info");
        if (encoded == null) return "";

        // Base64 解码 → JSON 解析
        String json = new String(Base64.getDecoder().decode(encoded));
        var map = JSON.parseObject(json);
        return map.get(key).toString();
    }
}
```

**`RequestContextHolder`** 是 Spring 的 ThreadLocal 工具。`getRequestAttributes()` 返回当前线程绑定的请求上下文。

**为什么用 Base64 而不是直接传 JSON？**

HTTP Header 不能包含非 ASCII 字符。Base64 编码保证 Header 值全是安全字符。

## 六、MyBatisPlus 逻辑删除

```java
@TableLogic
private Integer isDeleted;
```

```yaml
mybatis-plus:
  global-config:
    db-config:
      logic-delete-value: 1       # 已删除
      logic-not-delete-value: 0   # 未删除
```

**效果**：调用 `removeById(id)` 时，MyBatisPlus 自动把 SQL 改写为 `UPDATE doc_info SET is_deleted=1 WHERE id=?`——不会真的 DELETE。查询时自动加上 `WHERE is_deleted=0`。

**为什么用逻辑删除？**
文档可能有版本历史、权限记录等关联数据，物理删除会破坏数据完整性。逻辑删除保留数据，只是标记不可见。

## 七、MyBatisPlus 自动填充

```java
@TableField(fill = FieldFill.INSERT)
private LocalDateTime createTime;

@TableField(fill = FieldFill.INSERT_UPDATE)
private LocalDateTime updateTime;
```

配合 MetaObjectHandler：

```java
@Override
public void insertFill(MetaObject metaObject) {
    this.strictInsertFill(metaObject, "createTime", LocalDateTime.class, LocalDateTime.now());
}
```

插入或更新时，`createTime` / `updateTime` 自动填入当前时间——不需要在业务代码里手动 `doc.setCreateTime(LocalDateTime.now())`。

## 九、关键面试知识点

1. **为什么版本号递增而不是直接覆盖？**
   - 审计需求：谁在什么时候改了什么是可追溯的
   - 合规需求：企业文档可能需要保留历史版本
   - 回滚能力：误操作可以恢复

2. **分类树为什么一次查出来而不是递归查？**
   - N+1 查询问题是微服务性能杀手
   - 分类数据量小（几百条），一次 load 到内存做树组装更高效

3. **RabbitMQ 消息丢了怎么办？**
   - 队列声明 `durable=true`（持久化到磁盘）
   - 消息发送确认（publisher confirm）
   - 消费端手动 ACK（处理完才确认）

4. **为什么 publishEvent 用 Map 而不是序列化对象？**
   - 消费者可能不是 Java（档3 Python AI 服务）
   - Map → JSON 是跨语言通用格式
