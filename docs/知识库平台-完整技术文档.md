## 二、D1：项目骨架与技术选型

### 2.1 为什么选择这个技术栈

作为应届生简历项目，选 SpringCloud Alibaba 有几点考虑：

- Netflix 体系（Eureka + Ribbon + Hystrix）大部分已进入维护模式
- Alibaba 体系（Nacos + Sentinel + RocketMQ）在国内企业中使用更广
- Nacos 同时做注册中心和配置中心（Eureka + Config 二合一），减少运维组件

### 2.2 版本选择

```
Spring Boot 3.5.15    → 最新的 3.x 稳定版（JDK 17 最低要求）
Spring Cloud 2025.0.0 → 对应 Boot 3.5.x
SpringCloud Alibaba 2025.0.0.0 → 对应 Cloud 2025.0.0
JDK 17                 → LTS 版本，生产主流
```

**版本对齐非常重要**。Spring Boot → Spring Cloud → SpringCloud Alibaba 三者有严格的版本映射关系，错一个就启动报错。

### 2.5 为什么 Gateway 的 common 依赖要特殊处理

Gateway 基于 WebFlux（Netty），不能引入 Tomcat。但 common 模块原本依赖了 `spring-boot-starter-web`。

**解决方案**：common 模块不依赖 starter-web，改为细粒度依赖：

```xml
<dependency>
    <groupId>org.springframework</groupId>
    <artifactId>spring-web</artifactId>   <!-- 只引入 web 注解/工具，不带 MVC -->
</dependency>
<dependency>
    <groupId>jakarta.servlet</groupId>
    <artifactId>jakarta.servlet-api</artifactId>
    <scope>provided</scope>              <!-- 编译可用，不传递到下游 -->
</dependency>
```

`scope=provided` 的含义：编译时需要，但运行时由容器提供。Gateway 不引入 servlet-api，所以不会产生 WebFlux vs MVC 冲突。

### 2.7 common 模块设计

**统一响应体 ResponseResult**：所有 Controller 都用这个返回格式，前端统一解析：

```java
@Data
public class ResponseResult<T> {
    private int code;
    private String message;
    private T data;

    public static <T> ResponseResult<T> success(T data) {
        ResponseResult<T> r = new ResponseResult<>();
        r.code = 200;
        r.message = "success";
        r.data = data;
        return r;
    }

    public static <T> ResponseResult<T> fail(int code, String message) {
        ResponseResult<T> r = new ResponseResult<>();
        r.code = code;
        r.message = message;
        return r;
    }
}
```

**全局异常处理 GlobalExceptionHandler**：防止 Controller 抛异常时前端收到 Tomcat 的 HTML 错误页。

```java
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(BizException.class)
    public ResponseResult<?> handleBiz(BizException e) {
        return ResponseResult.fail(400, e.getMessage());
    }

    @ExceptionHandler(Exception.class)
    public ResponseResult<?> handleException(Exception e) {
        log.error("系统异常", e);
        return ResponseResult.fail(500, "服务器内部错误");
    }
}
```

**自动配置注册**：`UserContextUtil`、`GlobalExceptionHandler` 等放在 common 模块，需注册为自动配置：

```java
@AutoConfiguration
@Import({UserContextUtil.class, GlobalExceptionHandler.class})
public class CommonAutoConfiguration {
}
```

并创建文件 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`：
```
com.myy.common.config.CommonAutoConfiguration
```

这是 Spring Boot 3.x 新的自动配置注册方式（替代了旧的 `spring.factories`）。

## 三、D2-D3：API 网关 + 认证授权

### 3.1 Gateway 核心概念

**Gateway 是什么？** 微服务架构的"单入口"。所有外部请求先到 Gateway，再由 Gateway 根据路径转发到对应的微服务。好处：
- 前端只需要知道一个地址（8080），不用记每个服务的端口
- 鉴权在网关统一做，下游服务不用重复写

**WebFlux 和 SpringMVC 的区别：**

| | SpringMVC | WebFlux |
|---|---|---|
| 底层 | Tomcat + Servlet | Netty + Reactor |
| 线程模型 | 一个请求一个线程 | 事件驱动，少量线程 |
| 返回值 | `Object` | `Mono<T>` / `Flux<T>` |
| Filter | `javax.servlet.Filter` | `GlobalFilter` |
| 适用 | 业务服务（auth、doc等） | 网关 |

### 3.2 AuthFilter 详解

```java
@Component
public class AuthFilter implements GlobalFilter, Ordered {
```

**GlobalFilter**：Gateway 提供的全局过滤器接口，所有经过网关的请求都会进入 `filter()` 方法。

**Ordered**：决定多个 Filter 的执行顺序。`getOrder()` 返回 `-100` 表示高优先级（数值越小越先执行）。

**白名单机制**：
```java
private static final List<String> WHITE_LIST = Arrays.asList(
    "/auth/login", "/auth/register", "/auth/logout",
    "/file/download/", "/file/preview/"
);
```

**JWT 校验流程**：
1. 从 Header 拿 token：`Authorization: Bearer eyJhbG...`
2. 解析 JWT：签名不对 → SignatureException，过期 → ExpiredJwtException
3. 用户信息写入 Header 传给下游：`X-User-Info: Base64(JSON)`

**为什么要把用户信息写到 Header？**下游微服务直接从 Header 解码拿用户信息，不需要再重复验 token。Gateway 已经验过一次了。

**响应式写响应体**（WebFlux 特有）：
```java
private Mono<Void> unauthorized(ServerHttpResponse response, String message) {
    response.setStatusCode(HttpStatus.UNAUTHORIZED);
    byte[] bytes = JSON.toJSONString(ResponseResult.fail(401, message)).getBytes();
    DataBuffer buffer = response.bufferFactory().wrap(bytes);
    return response.writeWith(Flux.just(buffer));
}
```

不能用 `response.getWriter().write()`——那是 Servlet API。WebFlux 必须用 `DataBuffer` + `Flux` 来写响应。

### 3.4 Spring Security 核心配置

```java
@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http
        .csrf(AbstractHttpConfigurer::disable)          // ① 关闭 CSRF
        .sessionManagement(s -> s.sessionCreationPolicy(
            SessionCreationPolicy.STATELESS))             // ② 无状态 Session
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/auth/login", "/auth/register").permitAll()  // ③ 白名单
            .anyRequest().authenticated()
        )
        .formLogin(AbstractHttpConfigurer::disable)      // ④ 关闭表单登录
        .httpBasic(AbstractHttpConfigurer::disable)      // ⑤ 关闭 HTTP Basic
        .addFilterBefore(jwtFilter,                      // ⑥ 插入 JWT Filter
            UsernamePasswordAuthenticationFilter.class);
    return http.build();
}
```

① **关闭 CSRF**：前后端分离 + JWT 不需要 CSRF 防御（CSRF 依赖 Cookie-Session）。

② **无状态 Session**：不创建 `HttpSession`，状态全在 JWT Token 里。

③ **白名单**：`/auth/login` 和 `/auth/register` 不需要认证。

④⑤ **关闭表单登录和 HTTP Basic**：关掉 Spring Security 默认的登录页和弹窗认证。

⑥ **插入 JWT Filter**：在默认认证 Filter 之前执行我们的自定义 Filter。

### 3.5 认证流程

```
POST /auth/login {username, password}
    → AuthController.login()
    → authenticationManager.authenticate(token)
    → UserDetailsServiceImpl.loadUserByUsername()  // 查数据库
    → BCryptPasswordEncoder.matches(password, encoded)  // 验密码
    → 认证成功 → JwtTokenProvider.generateToken()  // 签发 JWT
    → 返回 { token, username, realName }
```

### 3.6 JWT 详解

**JWT 结构**：
```
eyJhbGciOiJIUzI1NiJ9.eyJ1c2VySWQiOjF9.SflKxw...
│                      │                 │
└── Header（算法）       └── Payload（数据）  └── Signature（签名）
```

三段 Base64 编码用 `.` 拼接。任何人拿到 token 都能解码 Payload（所以不要放密码），但无法篡改——Signature 是用密钥签名的。

```java
// 签发
Jwts.builder()
    .setClaims(Map.of("userId", 1, "username", "admin"))
    .setExpiration(new Date(now + 24*3600*1000))  // 24小时过期
    .signWith(SignatureAlgorithm.HS256, secret)
    .compact();

// 校验
Jwts.parser()
    .setSigningKey(secret)
    .parseClaimsJws(token)  // 签名不对→抛异常；过期→抛异常
    .getBody();
```

### 3.7 BCrypt 密码加密

同一个密码每次加密结果不同（自动加随机盐），不可逆——无法从密文反推明文。比对用 `matches(raw, encoded)` 而不是 `equals`。

```
"admin123" → BCrypt → "$2a$10$N.zmdr9k7uOCQb376NoUnu..."（每次不同）
```

### 3.8 Gateway Filter vs Auth Service Filter 的职责

| | Gateway AuthFilter | Auth Service JwtAuthFilter |
|---|---|---|
| 位置 | 网关层 | 业务服务层 |
| 触发范围 | 所有经过网关的请求 | 仅本服务请求 |
| 做什么 | 验 JWT → 注入 Header → 放行 | 验 JWT → 设 SecurityContextHolder |
| 失败处理 | 返回 401 JSON | 返回 401 JSON |

两个都能验 JWT，但各司其职：Gateway 提前拦截非法请求，Auth Service 内部也需要知道当前用户。

## 四、D4-D6：文档服务

### 4.1 模块结构

```

├── DocInfoController     7个REST接口（CRUD + 版本 + 分类 + ACL）
├── DocCategoryController 3个REST接口

### 4.2 文档版本管理

```
创建文档(version=1) → 更新(version+1) → 旧版本快照存 doc_version 表
用户回滚到v1 → version变成3（回滚操作本身也是一个新版本）
```

**关键点**：
- 只有上传新文件才触发版本号递增，只改标题/分类不触发
- `@Transactional` 保证 doc_info 更新和 doc_version 插入是原子操作
- 回滚操作本身也是一个新版本（不回退 version 字段，而是生成 version n+1）
- 版本表是追加写的（append-only），每个操作留痕

### 4.3 分类树

```sql
doc_category:
id | parent_id | name
1  | 0         | 技术文档     ← 根分类
2  | 1         | Java        ← 子分类
3  | 1         | Python
4  | 2         | Spring      ← 孙分类
```

**parent_id = 0 表示根节点**。树结构用 parent_id 自引用。

**递归组装树**：一次查出所有分类，内存里分组组装，时间复杂度 O(n)。不用递归查数据库（N+1 问题）。

**递归删除**：删除父分类时，自动级联删除所有子分类。

### 4.4 RabbitMQ 事件驱动

**为什么用 MQ？**
- 同步调用搜索服务：上传文档后要等 ES 索引完成才能响应——慢
- MQ 异步：发完消息就返回，ES 索引异步做——快
- 搜索服务挂了不影响文档创建——解耦

**配置**：TopicExchange + 4个队列（create/update/delete/audit），不同 Consumer 订阅不同 routing key。

**事件流向**：
```
doc.create ─→ search consumer (ES索引)
           ─→ audit consumer  (审计记录)
           ─→ embedding consumer (向量化)

doc.update ─→ search consumer (更新索引)
           ─→ audit consumer  (审计记录)

doc.delete ─→ search consumer (删除索引)
           ─→ audit consumer  (审计记录)
```

### 4.5 从 Gateway Header 取用户信息

**数据流回顾**：
```
Gateway AuthFilter → JWT 校验 → Claims → JSON → Base64 → X-User-Info Header
    ↓
Doc Service → UserContextUtil 从 X-User-Info 解码 → 拿到 userId、username
```

`RequestContextHolder` 是 Spring 的 ThreadLocal 工具。为什么用 Base64 而不是直接传 JSON？HTTP Header 不能包含非 ASCII 字符，Base64 编码保证 Header 值全是安全字符。

### 4.6 MyBatis-Plus 逻辑删除

```java
@TableLogic
private Integer isDeleted;
```

调用 `removeById(id)` 时，自动把 SQL 改写为 `UPDATE ... SET is_deleted=1`，不会真的 DELETE。查询时自动加上 `WHERE is_deleted=0`。

### 4.7 MyBatis-Plus 自动填充

`@TableField(fill = FieldFill.INSERT)` 配合 `MetaObjectHandler`，插入/更新时自动填入 `createTime` / `updateTime`，不需要在业务代码里手动 set。

## 五、D7：ACL 细粒度权限

### 5.1 两级权限模型

```
RBAC (sys_role_menu)        ACL (doc_acl)
───────────────              ──────────────
管"能不能进这个页面"        管"能不能看这篇文档"
粒度: 菜单级                 粒度: 单文档级
用户注册时分配角色           文档创建后单独授权
```

**为什么需要两级？** RBAC 只能控制到菜单——用户有 `doc:list` 权限就能进文档列表页。但进了列表页，不代表他能看所有文档。比如 HR 部门的薪酬文档，只应该让 HR 组的成员看。ACL 做的是"这篇文档谁能读、谁能改"。

### 5.2 数据表

```sql
doc_acl:
id | doc_id | user_id | perm_read | perm_write | perm_download | granted_by
1  | 100    | 5       | 1         | 0          | 0             | 1
```

每位（bit）代表一种权限，0=无，1=有。

### 5.3 权限判定逻辑

```java
public boolean hasPermission(Long docId, Long userId, String permission) {
    DocInfo doc = docInfoMapper.selectById(docId);
    // 创建者拥有全部权限
    if (doc.getCreatorId().equals(userId)) return true;

    // 查 ACL 表
    DocAcl acl = getOne(new LambdaQueryWrapper<DocAcl>()
            .eq(DocAcl::getDocId, docId)
            .eq(DocAcl::getUserId, userId));
    if (acl == null) return false;

    return switch (permission) {
        case "read"     -> acl.getPermRead() == 1;
        case "write"    -> acl.getPermWrite() == 1;
        case "download" -> acl.getPermDownload() == 1;
        default -> false;
    };
}
```

**关键设计决策**：创建者隐式拥有全部权限，不需要额外在 ACL 表里给自己加一条记录。避免了创建文档时还得插一条 ACL 的冗余操作。

### 5.4 AOP 权限切面

```java
@Aspect
@Component
public class DocPermissionAspect {
    @Before("@annotation(checkPermission)")
    public void checkPermission(JoinPoint jp, CheckDocPermission checkPermission) {
        Long docId = extractDocId(jp, checkPermission.paramName());
        if (docId == null) return;
        Long userId = userContextUtil.getCurrentUserId();
        docAclService.checkPermission(docId, userId, checkPermission.value());
    }
}
```

`@Before` 注解表示在目标方法执行**之前**拦截。如果权限校验失败抛出 BizException → 被 GlobalExceptionHandler 捕获 → 返回错误 JSON。目标方法不会被执行。

**为什么不用 Spring Security 的 `@PreAuthorize`？** `@PreAuthorize` 的 SpEL 表达式可以做方法级鉴权，但 ACL 的权限粒度到单篇文档，需要动态查数据库——`@PreAuthorize` 做不到"查 doc_acl 表判断用户对 docId=123 是否有 write 权限"。自写 AOP 可以从方法参数取 docId、调 Service 查 ACL 表，灵活性更高。

### 5.5 前端 ACL 权限管理（三次 UX 迭代）

**第一版（失败）**：手动输入用户 ID 的 `<el-input type=number>`。用户需要记住或查询目标用户的 ID 再填入，实际完全不可用。

**第二版（失败）**：改为搜索选择用户 + 三个 checkbox + "授权"按钮的两区域布局。问题：用户不理解"选人 → 勾权限 → 点授权"的操作路径；`el-select` 的 `v-model` 是字符串 `''` 而 `:value` 是数字类型，`filterable` 模式下类型不匹配导致选不中。

**第三版（最终方案）**：单表内联编辑模式。

```
表格：用户列 | 读(Switch) | 写(Switch) | 下载(Switch) | 操作(保存/移除)

已有行：显示用户名，Switch 切换即时自动保存（@change → POST API）
新建行：点"+ 添加用户权限"，用户列变下拉框，Switch 设置权限，点"保存"提交
```

核心改进：
- 一张表完成所有操作，不用切换视线
- 已有行 Switch 自动保存，无需额外按钮
- 已授权用户在新建下拉框中 `:disabled`，防止重复
- `Promise.allSettled` 并行加载用户列表和 ACL 数据
- `v-loading` 的开关包在 `try-finally` 中防止转圈卡死

## 六、D8-D9：MinIO 文件服务 + 分片上传

### 6.1 MinIO 是什么

MinIO 是一个兼容 Amazon S3 API 的开源对象存储。可以理解为自己搭的"私有 AWS S3"。

**为什么不用服务器本地磁盘？** 微服务多实例部署时，文件存 A 实例磁盘，B 实例读不到。MinIO 是独立服务，所有实例共享访问。

### 6.2 MinioClient Bean

```java
@Configuration
@ConfigurationProperties(prefix = "minio")
public class MinioConfig {
    private String endpoint;
    private String accessKey;
    private String secretKey;

    @Bean
    public MinioClient minioClient() {
        return MinioClient.builder()
                .endpoint(endpoint)
                .credentials(accessKey, secretKey)
                .build();
    }
}
```

### 6.3 Bucket 自动创建

独立的 `MinioBucketInitializer` 组件，通过构造器注入已创建好的 `MinioClient`，在 `@PostConstruct` 中检查并创建 bucket。决不能和 `MinioConfig` 放在同一个类里（会产生 Spring 循环引用）。

### 6.4 小文件上传

```
前端选择文件 → POST /file/upload (multipart/form-data)
    ├─ 校验文件类型 (MIME白名单)
    ├─ 校验文件大小 (<10MB)
    ├─ 计算 MD5
    ├─ MinIO putObject
    ├─ 写入 file_info 表
    └─ 返回 FileInfo (含 fileKey、size、md5)
```

**文件 Key 设计**：`2026-06/3f7a2b1c/Spring Boot入门.pdf`。按日期分区避免单个目录下文件过多，UUID 短码防重名。

**文件类型校验**：只允许 PDF/DOC/PNG/JPEG/TXT 等，防止用户上传 exe、脚本等不安全文件类型。

### 6.5 分片上传三阶段

```
[1] POST /file/chunk/init
    ├─ MD5秒传检测 → 命中则直接返回已有文件URL
    ├─ 生成 uploadId + fileKey
    ├─ Redis 记录元数据 (totalChunks, fileSize, ...)
    ├─ 创建 file_info 记录 (status=UPLOADING)
    └─ 返回 { uploadId, fileKey, skipUpload: false }

[2] POST /file/chunk/upload  (调用 N 次)
    ├─ 从 Redis 读上传会话
    ├─ MinIO putObject → tmp/{uploadId}/{chunkIndex}
    └─ Redis 标记分片已上传 + 增加 uploadedCount

[3] POST /file/chunk/merge
    ├─ 校验所有分片已到齐
    ├─ MinIO composeObject → 合并临时对象 → 最终文件
    ├─ 清理临时分片
    ├─ 更新 file_info 状态 → COMPLETED
    └─ 清理 Redis
```

**秒传原理**：文件 MD5 指纹 + 文件大小构成唯一标识。同一份文件，不同用户上传，只需存一份。

**为什么用 composeObject 而不是下载后重新上传？** composeObject 是 MinIO 服务端操作，数据不经过我们的服务器。合并 500MB 的文件，下载→重新上传需要 2× 网络传输 + 内存占用。

**Redis 追踪上传进度**：分片上传是临时状态，Redis TTL 自动清理过期会话（24 小时后自动删除）。

### 6.6 文件下载

流式输出——`stream.transferTo(response.getOutputStream())` 边读边写，不把整个文件 load 进内存。500MB 的文件如果用 `byte[] bytes = stream.readAllBytes()`，JVM 直接 OOM。

### 6.7 文件与文档的关联设计

```
file_info.doc_id → doc_info.id  (一个文档关联多个文件)

创建流程：保存文档(得docId) → 上传文件(带docId) → file_info写入关联
查看流程：GET /doc/{id} 获取文档详情 + GET /file/by-doc/{id} 获取附件列表
```

- **文件存文档 ID**：`file_info.doc_id` 外键关联，支持一个文档上传多个附件
- **下载/预览白名单**：Gateway 添加 `/file/download/` 和 `/file/preview/` 到白名单，允许不携带 Token 的浏览器直接访问（如 `<img src>` 标签加载水印图片）

## 七、D10-D11a：水印 + 在线预览

### 7.1 为什么需要水印

- 用户截图或下载后可以直接传播，无法追溯到泄露源头
- 水印叠加当前用户信息和时间戳，即使被截图/转发，也能追溯到是谁在什么时间点获取的文件

### 7.2 水印内容与样式

```
张三 @ 2026-06-27 15:32
倾斜 -30°，浅灰色，半透明（alpha=24%），平铺覆盖整个页面
```

**为什么倾斜？** 水平排列容易被裁剪或覆盖，倾斜的水印更难被修图工具去除。

**为什么半透明？** 不阻挡正文阅读，但截图后仍然清晰可辨。

**为什么平铺？** 覆盖整个页面，无论裁切哪个区域都有水印。

### 7.3 策略模式

```
文件请求 → 判断MIME
    ├─ image/*      → Java 2D Graphics（JDK 内置，零依赖）
    ├─ application/pdf → Apache PDFBox（矢量操作，Matrix 变换）
    └─ 其他格式     → 原样返回（doc/ppt 等暂不支持）
```

### 7.4 图片水印实现

```java
BufferedImage image = ImageIO.read(new ByteArrayInputStream(imageBytes));
Graphics2D g2d = (Graphics2D) image.getGraphics();
g2d.setColor(new Color(128, 128, 128, 60));  // 灰色 + 半透明

// 倾斜平铺
for (int y = -imgH; y < imgH * 2; y += 200) {
    for (int x = -imgW; x < imgW * 2; x += 400) {
        g2d.rotate(-30°, x, y);
        g2d.drawString(text, x, y);
        g2d.rotate(30°, x, y);
    }
}
```

输出统一用 PNG——PNG 支持透明度通道，水印的半透明效果才能保留。

### 7.5 PDF 水印实现

PDF 是矢量的（描述性指令），不能像图片一样操作像素。需要解析 PDF 文档结构，在每一页的 ContentStream 上追加文字流。

使用 PDF 变换矩阵实现旋转：
```
[a b 0]
[c d 0]   →   new Matrix(cosθ, sinθ, -sinθ, cosθ, x, y)
[e f 1]
```

### 7.6 预览 vs 下载

| | inline | attachment |
|---|---|---|
| Content-Disposition | inline | attachment |
| 浏览器行为 | 直接渲染 | 弹出另存为对话框 |
| 使用场景 | 在线预览 | 下载到本地 |

两者都带水印，但预览的水印是动态的（包含当前用户+时间）。

### 8.2 ES 索引设计

```java
@Data
@Document(indexName = "knowledge_doc")
public class DocDocument {
    @Id
    private Long id;             // 与 MySQL doc_info.id 一致

    @Field(type = FieldType.Text, analyzer = "ik_max_word")
    private String title;

    @Field(type = FieldType.Text, analyzer = "ik_max_word")

    @Field(type = FieldType.Long)

    @Field(type = FieldType.Keyword)

**`title^3` 的含义**：title 字段权重为 content 的 3 倍。标题命中比正文命中更相关。

### 8.3 搜索 DSL 构建

```java
NativeQuery query = NativeQuery.builder()
    .withQuery(QueryBuilders.boolQuery()
        .must(QueryBuilders.multiMatchQuery(keyword, "title^3", "content"))
        .filter(QueryBuilders.termsQuery("id", visibleIds))   // 权限过滤
        .filter(QueryBuilders.termQuery("status", "PUBLISHED"))
    )
    .withHighlightQuery(new HighlightQuery(
        new Highlight("title", "content")
            .setPreTag("<em>").setPostTag("</em>")))
    .withPageable(Pageable.ofSize(pageSize).withPage(pageNum - 1))
    .build();
```

**must vs filter**：must 参与评分（匹配度越高分越高），filter 不参与评分只过滤，速度快且结果可缓存。权限是二元的（有或无），不需要"匹配度"，所以用 filter。

### 8.4 Redis 热搜统计

**为什么用 Redis ZSet？** ZSet 是有序集合，每个元素有一个 score。热搜场景天然适合：

```
ZSet key: hot:search:keywords
members: "请假流程"→156, "Spring Boot"→89, "薪酬制度"→45
```

**热搜质量保障**：只在搜索到结果时才记录关键词。

```java
// 先执行搜索 → 拿到 total
Object total = result.get("total");
if (total instanceof Number && ((Number) total).longValue() > 0) {
    searchService.recordSearch(keyword);  // 只有搜到了才计入热搜
}
```

### 8.5 权限过滤搜索

**数据流**：
```
SearchController → UserContextUtil 取 userId
    → Feign 调 doc 服务 GET /doc/visible-ids
    → 返回用户可见文档 ID 列表
    → Feign 失败 → fallback 返回空列表（安全优先）
    → ES Query termsQuery("id", visibleIds) 预过滤
```

**fail-safe 原则**：无权限直接返回空，不做 ES 查询。之前有个 fail-open 的 bug——空列表时 filter 跳过导致全库泄露，修复后改为 deny-by-default。

### 9.2 和版本管理的区别

- 版本管理记录的是"文档内容变到什么版本"（数据视角）
- 审计日志记录的是"谁做了什么操作"（安全视角）
- 两者互补，一个关注 What，一个关注 Who+When

### 9.3 数据库设计

```sql
CREATE TABLE audit_log (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    doc_id BIGINT COMMENT '关联文档ID',
    doc_title VARCHAR(255) COMMENT '文档标题（冗余，历史标题）',
    action VARCHAR(20) COMMENT '操作类型：CREATE/UPDATE/DELETE/VIEW',
    operator_id BIGINT COMMENT '操作人ID',
    operator_name VARCHAR(100) COMMENT '操作人用户名',
    detail TEXT COMMENT '操作详情（JSON 格式）',
    ip_address VARCHAR(45) COMMENT '客户端IP',
    create_time DATETIME COMMENT '操作时间',
    INDEX idx_doc_id (doc_id),
    INDEX idx_operator_id (operator_id),
    INDEX idx_create_time (create_time)
);
```

**为什么冗余 doc_title？** 文档可能被删除，如果只存 doc_id，日志里显示"文档#123 被删除"，看不懂。冗余标题后日志显示"《薪酬制度 V3》被删除"——信息完整。

**detail 用 TEXT + JSON 格式**：不同操作类型的详情结构不同，用 JSON 灵活存储，不限制 schema。

├── KnowledgeSearchTool 知识检索工具     ├── EmbeddingService    向量化 API

└── SessionMemoryService Redis 记忆

### 11.2 什么是 RAG Agent

**RAG（Retrieval-Augmented Generation）**：用户提问 → 检索相关文档 → 把文档片段塞进 Prompt → LLM 基于片段回答。LLM 回答有了"引经据典"的依据，而不是凭空编造。

**Agent（Function Calling 模式）**：让 LLM 自己判断是否需要检索、检索什么、检索结果够不够。如果 LLM 觉得信息不够，它可以再调用一次工具，换关键词重新搜。最多 3 轮。

### 11.3 Agent 主循环

```
用户提问
    ↓
LLM 判断是否需要工具
    ├─ 有 tool_calls → 执行工具调用（注入权限）→ 反馈结果给 LLM → 回到判断（最多3轮）
    └─ 有 content → 返回最终答案
```

核心代码：
```java
for (int turn = 0; turn < maxTurns; turn++) {
    LLMResponse llmResp = llmClient.chat(messages, toolRegistry.getDefinitions());
    
    if (llmResp.isFinished() && llmResp.getContent() != null) {
        return buildResponse(llmResp.getContent());
    }
    
    for (ToolCall tc : llmResp.getToolCalls()) {
        String result = toolRegistry.execute(tc.getName(), tc.getParams());
        messages.add(工具调用结果);
    }
}
return forceFinalAnswer(messages);
```

### 11.4 三层权限保障

1. **网关层**：AuthFilter 校验 JWT
2. **工具调用层**：AgentOrchestrator 向工具参数注入 userId 和 accessToken
3. **检索服务层**：knowledge-search 根据 userId 过滤 `doc_acl` 表

    log.warn("幻觉工具调用: {}", raw.getName());

### 11.6 两个工具

**knowledge_search**：在知识库中检索文档，返回相关片段。实际调用 `GET /search`，带上 Token，只返回有权限的结果。

**list_knowledge_tree**：查询知识库的目录结构。调用 `GET /doc/category/tree`。

### 11.7 DeepSeek Function Calling

API 完全兼容 OpenAI 格式（`/v1/chat/completions`），国内直接访问。

两种响应：
- `finish_reason: "stop"` → LLM 直接回答
- `finish_reason: "tool_calls"` → LLM 发起工具调用，返回 JSON 格式的工具名+参数

### 11.8 嵌入式向量化流水线

```
文档创建 → MQ → DocEmbedConsumer
    → ChunkService.split()（滑动窗口：max 500字符，overlap 50字符）
    → EmbeddingService.embed()（调用 BGE 模型 → 1024维向量）
    → saveAll() 批量写入 ES knowledge_chunks 索引
```

**为什么 overlap？** 如果严格按句号切分，可能把一个概念的上下文切断。overlap 让相邻 chunk 有部分重叠，减少信息断裂。

### 11.9 OOM 修复

**根因（三层叠加）**：
1. 逐 chunk `save()` → N 个 chunk = N 次 HTTP 往返 + JSON 序列化
2. `float[1024]` 向量 JSON 序列化后约 16KB
3. 无 JVM 堆配置

**修复**：逐条 → `saveAll()` 批量写入；JVM `-Xms256m -Xmx512m`；ES 客户端加超时；ChunkService 修复死循环。

### 11.10 Redis 会话记忆

```
Key:   agent:session:{sessionId}
Value: [{"role":"user","content":"..."},{"role":"tool","content":"..."}]
TTL:   30 分钟
```

只保留最近 20 条消息，超出 LLM 上下文窗口时自动截断（从最早的用户消息开始删，保留 system message）。

## 十二、踩坑记录

### 12.1 Spring 基础设施

#### UserContextUtil Bean 注入失败

**现象**：`knowledge-doc` 启动报 `NoSuchBeanDefinitionException: UserContextUtil`。

**根因**：`UserContextUtil` 提取到 `knowledge-common` 的 `com.myy.common.config` 包下，但 Spring Boot 的 `@ComponentScan` 默认只扫描启动类所在包。

**修复**：创建 `CommonAutoConfiguration.java`（`@AutoConfiguration` + `@Import(UserContextUtil.class)`），并在 `META-INF/spring/...AutoConfiguration.imports` 注册。

#### Gateway WebFlux 与 Spring MVC 冲突

**现象**：Gateway 启动报 `Spring MVC found on classpath, which is incompatible with Spring Cloud Gateway`。

**根因**：`knowledge-common` 依赖 `spring-boot-starter-web`（含嵌入式 Tomcat）。Gateway 引入 common 后 classpath 上同时存在 WebFlux 和 Spring MVC。

**修复**：将 common 依赖改为细粒度的 `spring-web` + `jakarta.servlet-api(provided)`。

#### Feign `lb://` 调用报 No Feign Client for loadBalancing

**现象**：`lb://knowledge-doc` 调用时报未定义负载均衡器。

**根因**：Spring Cloud 2025.x 中 `spring-cloud-starter-openfeign` 不再自动引入负载均衡器。

**修复**：手动添加 `spring-cloud-starter-loadbalancer`。

### 12.2 Java 基础陷阱

#### Map.of() 抛 NullPointerException

**现象**：`AgentOrchestrator` 报 NPE，定位到 `Map.of("role", "assistant", "content", null, ...)`。

**根因**：Java 9+ `Map.of()` 对所有 value 执行 `Objects.requireNonNull()`。但 OpenAI Function Calling 协议要求 `assistant` 消息在有 `tool_calls` 时 `content` 必须为 `null`。

**修复**：改用 `LinkedHashMap` 逐项 put，允许 null value。

### 12.3 Elasticsearch

#### Date Format 不匹配导致搜索 500

**现象**：`Unable to convert value '2026-07-01' to java.time.LocalDateTime`。

**根因**：`@Field(format = DateFormat.date_hour_minute_second)` 注解后来加入，但 ES 索引在注解前已创建。已有数据为纯日期 `2026-07-01`，新 format 要求 `yyyy-MM-dd'T'HH:mm:ss`。

**修复**：删索引 → 重建正确 mapping → reindex 回填数据。新增 `POST /search/admin/reindex` 运维端点。

#### Embedding 服务 OOM（Dense Vector 序列化）

**现象**：`knowledge-embedding` 消费 MQ 消息时 `OutOfMemoryError: Java heap space`。

**根因**：逐 chunk save() + `float[1024]` JSON 膨胀到 ~16KB + 无 JVM 堆配置。

**修复**：`saveAll()` 批量写入；JVM 参数 `-Xms256m -Xmx512m`；ES 客户端加超时；ChunkService 死循环修复。

#### 嵌入服务死循环 → 加剧 OOM

**现象**：ChunkService.split() 在文本长度恰好等于 maxSize 时无限循环。

**根因**：`end >= text.length()` 后，`start = end - overlap` 计算得 `500 - 50 = 450`，下次循环重复添加同一个 chunk。

**修复**：添加 `if (end >= text.length()) break;` 和 `start <= 0 || start >= end` 双重守卫。

### 12.4 安全漏洞

#### 搜索权限绕过 — 新用户能看到所有文档

**现象**：新注册用户搜索任何关键词都能看到 admin 的私有文档。

**根因**：`visibleIds` 为空时 filter 被跳过，ES 裸查返回全库文档。这是 **fail-open**（失败放行），安全设计大忌。

**修复**：改为 **fail-safe**——无权限直接返回空，不做查询。

**面试要点**：OWASP Top 10 #1 就是 Broken Access Control，这个 bug 是典型案例。

### 12.5 架构设计

#### 热搜关键词与实际文档不匹配

**现象**：热搜榜出现大量关键词，点击后搜索结果为空。

**根因**：`recordSearch(keyword)` 在搜索执行**之前**调用。

**修复**：先执行搜索，`total > 0` 才记录关键词。

#### MinIO Bucket 不存在 + Spring 循环引用

**现象**：文件上传报 `The specified bucket does not exist`。

**根因**：bucket 未创建。首次尝试在 `MinioConfig` 的 `@PostConstruct` 中调用本类的 `minioClient()` `@Bean` 方法，触发循环引用。

**修复**：将 bucket 初始化逻辑提取到独立的 `MinioBucketInitializer` 组件，通过构造器注入已创建好的 `MinioClient`。

### 12.6 前端

#### ACL 权限管理的 UX 设计迭代（三次重构）

详细过程见第五节 5.5。

第一版：手动输入用户 ID → 不可用
第二版：搜索选择器 + 两区域布局 → 类型不匹配 + 操作路径不清晰
第三版：单表内联编辑，Switch 自动保存 + 新建行选择保存

#### Vue `{{ }}` 在 HTML 属性中显示原始模板

**现象**：`:title="'思考过程 (' + msg.thoughtTrace.length + ' 步)'"` 显示为原始字符串。

**根因**：Vue `{{ }}` 只在文本内容节点生效，不能用于 HTML 属性值。

> **架构方面**：拆分为 10 个微服务模块，Gateway 统一入口自实现 GlobalFilter 做 JWT 鉴权，用户信息 Base64 透传下游。文档服务采用 AOP + 自定义 @CheckDocPermission 注解实现声明式权限检查，支持文档级 ACL 三粒度（读/写/下载）授权。文件服务采用 `file_info.doc_id` 关联文档设计，支持一个文档多个附件，MinIO 分片上传 + MD5 秒传 + 动态水印防泄露。RabbitMQ 事件驱动，文档变更异步同步 ES 全文索引和向量索引。
>
> **RAG 链路**：自实现 Agent Orchestrator 主循环——LLM 通过 Function Calling 自主判断是否需要检索，动态调用知识库搜索和分类树工具。搜索结果基于 ES Dense Vector kNN 语义检索返回相关片段。工具调用经过白名单过滤 + 参数校验 + 权限注入三道安全关卡。Redis 存储会话记忆（最近 20 条 + TTL 30 分钟），上下文超限自动截断。
>
> **技术深度**：独立排查并修复了多个非 trivial 故障——Embedding 服务 OOM（根因：Dense Vector JSON 序列化膨胀 + 批量写入缺失 + 死循环）、搜索权限 fail-open 漏洞（OWASP Broken Access Control 典型案例）、ES Date Format schema 变更导致 500、ACL 前端交互从"手动输入 ID"到"单表内联编辑"三次迭代优化等。全程通过 jps/jstat/HeapDump 完成 JVM 内存诊断。
>
> **前端**：Vue3 + Element Plus，响应式布局，搜索高亮、分类树多选、文档版本回溯、Agent 对话思考链可视化等功能。

### 13.9 面试追问 & 参考答案

**Q: RAG 和直接调 LLM 有什么区别？**
> 直接调 LLM 回答基于训练数据，无法获取企业内部最新文档。RAG 先检索知识库再让 LLM 基于检索结果回答，保证答案可追溯、可验证，且能覆盖私有数据。本项目用的是 ES Dense Vector kNN 做语义检索，比关键词匹配更理解语义。

**Q: Agent Function Calling 的工作流程？**
> 1. 用户提问 → Orchestrator 组装 system prompt + 历史消息 + 工具定义 → 发给 LLM
> 2. LLM 返回 tool_calls（如 knowledge_search）而不是直接回答
> 3. Orchestrator 校验工具白名单 + 参数 → 执行工具 → 结果反馈给 LLM
> 4. 循环直到 LLM 判断信息足够返回 final answer，或达到 max_turns（3 轮）

**Q: 搜索权限是怎么做的？**
> 先调 ACL 服务查用户可见文档 ID 列表，再作为 ES terms filter 条件拼到查询里。关键设计是 fail-safe：visibleIds 为空时直接返回空结果，不做 ES 查询。之前有个 fail-open 的 bug——空列表时 filter 跳过导致全库泄露，修复后改为 deny-by-default。

**Q: 嵌入服务 OOM 怎么排查的？**
> jps 找到进程 PID → jstat -gcutil 观察 O 列（Old Gen）持续到 100% → Full GC 频繁但无法回收 → 确认内存泄漏或单次加载过大。HeapDump 分析发现 httpasyncclient 线程堆积大量 float[] 序列化后的 JSON 字符串。根因：每个 chunk 单独 save() + Dense Vector JSON 膨胀 + 文本切片死循环。

**Q: 为什么用 RabbitMQ 而不是直接调？**
> 解耦 + 削峰。文档创建后同步调 Embedding 会让用户等待。用 MQ 异步后：文档服务只发消息即返回，embedding 和 search 各自消费，互不影响，失败了也可以重试。
